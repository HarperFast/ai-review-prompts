# Harper v5 conventions

Review guidance for repos that target Harper v5. Apply this layer when the repo's `peerDependencies` declares `harper`.

> **Authoritative source.** `HarperFast/skills/harper-best-practices/` is the customer-facing guidance for building on Harper. This document is a **review lens** — what to CHECK when reviewing changes. If anything here contradicts the skills, the skills win for user-facing guidance; this file's job is reviewer discipline.

## Package and CLI

- **Package**: `harper`. Imports: `from 'harper'`. Peer dep range: `harper >=5.0.0`.
- **CLI binary**: `harper` (e.g., `harper deploy_component`). PR diffs introducing v4-era `harperdb` imports or `harperdb` CLI calls are stale — flag them.

## Resource API v2

v5 has two co-existing dispatch patterns. A review of any Resource — or anything that wraps a Resource — must account for BOTH.

- **Instance-method pattern**:

  ```ts
  class MyResource extends Resource {
    static loadAsInstance = false;
    async get(target) {
      const request = this.getContext();
      ...
    }
  }
  ```

  Harper's Resource base static `get` is `transactional(fn)` — it creates a per-request instance and calls the instance method.

- **Static-method pattern** (v5 migration guide explicitly recommends this):

  ```ts
  class MyResource extends Resource {
    static async get(target, request) { ... }
  }
  ```

  Harper's REST dispatcher calls `Class.get(target, request)` at the STATIC level. The user's static shadows the Resource base's transactional static — no instance is created.

- **Wrappers must cover both surfaces.** A wrapper that intercepts only instance methods is silently bypassed when the user adopts the static-method pattern. Full coverage wraps both and de-duplicates work (e.g. via a WeakSet keyed by the request context) so a single dispatch doesn't run validation twice.

- **405 vs 204.** Harper's REST dispatcher returns `405 Method Not Allowed` when the method is undefined on the resource. A wrapper that defines all five verbs unconditionally — even when the parent doesn't implement them — replaces `undefined` with a function that returns `undefined`, and Harper serializes that as `204 No Content`. Only wrap verbs the parent actually implements.

## Context + `getContext()`

- Request-scoped state lives on the context returned by `this.getContext()` (inside an instance method). For static methods, Harper passes the request as the second arg: `static async get(target, request)`.
- `this.getCurrentUser()` returns the authenticated user off the current context. Checks against `user.role.permission.super_user` are the standard "require superuser" guard.
- `scope.resources` and `scope.server` are typed as optional in v5 but always assigned in the Scope constructor (`components/Scope.ts:70-71`). Plugins should guard once at `handleApplication` entry and use narrowed locals.

### Access control: verify the model, not just its presence

When a change adds an RBAC/permission walk (super_user, table-level read/describe, attribute permissions) on a Resource **enumeration/listing** surface — including MCP `resources`/`tools` listing — confirming a walk *exists* is not the same as confirming it's the *right* walk. Check the model:

- **Per-record access vs list-time permission walk.** Harper Resource access is determined per-record/programmatically by each subclass's `allow{Read,Create,Update,Delete}` predicates. Gating a *listing* on the caller's table permissions is often the wrong model — listing should key off REST-verb presence (`hasRestVerbs`) / the resource's declared surface, not a `userTablePermissions` walk. A permission check that doesn't reflect how access is actually enforced is misleading, not protective.
- **Protocol/`exportTypes` gating.** A Resource can be exported for some protocols and disabled for others. Verify enumeration consults the export/protocol gate so a Resource disabled for the HTTP/default type isn't still enumerable and readable over MCP (MCP surface wider than REST). There should be a way to expose over REST but disable for MCP, and vice versa.
- **Role identifiers must be grantable.** A role check is dead if it references an internal-only identifier that is never role-grantable (e.g. `cluster_user` on `AuthedUser` is internal, not a grantable role). Verify role names in `canRoleInvokeOperation`-style allowlists are real, grantable roles.

These are blockers when the enumeration/listing surface is reachable in production and the wrong model can expose, hide, or authorize resources incorrectly; if the surface is unreachable or intentionally broader/narrower, say why rather than flagging.

## `config.yaml` and resource loading

(How `jsResource.files` / `graphqlSchema.files` configure loading is owned by `harper-best-practices` — `rules/custom-resources.md`, `rules/schema-design-tooling.md`; consult those for the mechanics.) The review lens:

- A change to `jsResource.files` (glob / pattern / directory / extension) IS a meaningful review concern — it changes what actually gets served.
- `config.yaml` also carries the plugin entry point (`pluginModule`) and runtime defaults (e.g. `redirectUri`, `scope`, `defaultRole`). Treat `config.yaml` changes as code, not docs — a typo breaks the plugin/app at runtime.

## Environment variables and `.env`

The mechanics — `dotenv-cli` in the app template, Harper reading `process.env.*`, and the app-root `.env` deploying alongside the component to Fabric — are owned by `harper-best-practices` (`rules/creating-harper-apps.md`, `rules/deploying-to-harper-fabric.md`). Consult those rather than re-explaining them in-repo (per the "defer to Harper docs/skills" rule in `common.md`). The review-lens checks:

- **Deploy credentials ≠ runtime secrets.** `CLI_TARGET*` authenticate the deploy CLI (loaded in the deploy shell, NOT shipped with the app); runtime app secrets (`OAUTH_GITHUB_CLIENT_ID`, etc.) come from the deployed `.env`. Flag any doc or change that conflates them — e.g. a GitHub Actions `env:` block assumed to propagate to the runtime.
- **Recommendations must match Harper's toolchain** — `.env` via `dotenv-cli` for local/CI/deploy credentials, deployed `.env` for Fabric runtime. Flag generic systemd / Kubernetes-secret / cloud-secrets-manager advice unless the author explicitly asked about non-Fabric deployment.

## Deployment: Fabric

Harper v5's managed production platform is Fabric.

- **Authoritative references** in `HarperFast/skills`: `harper-best-practices/rules/deploying-to-harper-fabric.md`, `harper-best-practices/rules/creating-a-fabric-account-and-cluster.md`.
- Default deployment recommendations go to Fabric. Alternatives are for users who explicitly opt out.

## Typing

- Imports from `harper` — v5 exports `Resource`, `Scope`, `User`, `RequestTarget`, `Context`, `SourceContext`, and others. Verify imports against the v5 `index.d.ts`.
- Harper v5 has pre-existing TS errors in its own source that surface during consumer `tsc` runs; repos use `tsc || true` to tolerate these. Do NOT flag type errors originating from `node_modules/harper/` as blockers — they're upstream.
